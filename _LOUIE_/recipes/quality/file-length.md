Scan every source file against the 800-line cap and capture each file over it as a refactoring entry in the roadmap.

# File Length Audit

**Recipe type:** audit. This recipe produces a report and roadmap entries. It never writes application code and never runs the feature chain — see `_LOUIE_/recipes/README.md` § Recipe Types.

## Overview

`_LOUIE_/guidelines/coding-guidelines.md` caps source files at **800 lines** and calls an overrun a critical violation during review. That cap is enforced per-file at review time, which means it only ever sees the files a given change touched. Files that grew past the cap before the rule mattered — or in code nobody has reviewed lately — stay invisible.

This recipe closes that gap: one sweep over the whole codebase, one line count per file, and every file over the cap becomes a tracked refactoring entry in `_LOUIE-output/roadmap.md`. Refactoring a 1200-line file is epic-sized work, not a quick change, so the roadmap — the project's pre-feature-folder epic list — is the right home for it.

The audit is deliberately re-runnable. Running it again after six months must not duplicate entries, and must notice files that dropped back under the cap.

### Use this when

- Onboarding an existing codebase into LOUIE (right after `louie-import`), to seed the refactoring backlog.
- Periodically — a quarterly or per-release health check.
- Before a large feature lands in an area you suspect has bloated files.

### Do not use this for

- **Fixing anything.** This recipe files work; it does not do it. Splitting a file is `louie-roadmap promote <id>` → `louie-feature`, or `louie-update` when the split is genuinely small.
- **A general quality assessment.** Function size, dead code, DRY, over-engineering, security → `louie-evaluate`, which covers file size as one of many categories and carries its own apply loop.
- **Function-level or complexity limits.** Out of scope here; one standard per audit recipe.

## Threshold

**800 lines**, sourced from `_LOUIE_/guidelines/coding-guidelines.md`. Read the guideline at run time rather than trusting this number — if a project amended its cap, the guideline wins.

The user may pass a different threshold for a single run (`louie-recipe quality:file-length 500`). That override applies to the run only. **Never edit the guideline** to match an ad-hoc threshold; if the user wants the project's cap changed permanently, that's a separate, explicit edit they ask for.

A line is a **physical line** — `wc -l`, blanks and comments included. That is the unit the guideline is written in; changing it (see *Variations*) changes what "800" means and must be stated in the report.

## Audit Procedure

### 1. Resolve scope

Default scope is the repository root. The user may scope to a subpath (`louie-recipe quality:file-length src/api`). Announce the scope in the report — a subpath scan that reads like a whole-repo scan is a misleading clean bill of health.

### 2. Enumerate candidate files

Prefer `git ls-files` over a filesystem walk: it respects `.gitignore` for free and excludes build output, caches, and untracked scratch files, which are the bulk of the false positives here.

```
git ls-files -- <scope>
```

Non-git projects: walk the tree, skipping `node_modules`, `vendor`, `dist`, `build`, `target`, `out`, `.venv`, `venv`, `__pycache__`, `.git`, and any directory the project's ignore files name.

### 3. Keep only source files

Read `_LOUIE-output/tech-stack.md` (if it exists) and keep the extensions of the project's actual languages. Without a tech stack, fall back to a broad set: `.ts .tsx .js .jsx .mjs .cjs .py .rb .go .rs .java .kt .swift .cs .c .h .cpp .hpp .php .scala .ex .exs .dart .vue .svelte .sql .sh` plus the project's styling and template extensions where those hold real logic.

Configuration, documentation, and data files are **not** code: `.json .yaml .yml .toml .md .csv .lock` and similar are out of scope. A 3000-line data fixture is not a refactoring target.

### 4. Exclude generated and vendored code

Exclude, because refactoring these is either impossible or means changing a generator instead:

- Lockfiles and dependency manifests' generated halves.
- Minified or bundled output — `*.min.*`, `*.bundle.*`, source maps.
- Vendored third-party code — `vendor/`, `third_party/`, anything checked in from upstream.
- Code-generated clients and stubs — OpenAPI/protobuf/GraphQL codegen, ORM schema dumps, generated parsers. Detect by the generator header (`// Code generated by …`, `@generated`, `DO NOT EDIT`) as well as by path.
- Database migrations and test snapshots/fixtures — append-only by design.
- Translation and message catalogs.

**Every exclusion is reported, with its reason.** A file that silently disappears from an audit is worse than a file that was never checked — list them under an *Excluded* count in the report so the user can challenge a call.

### 5. Count and compare

Count physical lines per remaining file, keep those over the threshold, sort descending by line count.

### 6. Record the measurement context

Capture today's date and the short git SHA of `HEAD`. Both go into every roadmap entry — a line count without a commit is unverifiable six months later.

## Findings Report

Report to the user **before** touching the roadmap. Structure:

```
File-length audit — threshold 800 lines
Scope: <repo root | subpath>   ·   HEAD: <short-sha>   ·   <YYYY-MM-DD>

Scanned: <N> source files   Excluded: <M> (generated/vendored)   Over the cap: <K>

  <path>                      <lines>   (+<over>)
  <path>                      <lines>   (+<over>)
  ...
```

Then the excluded list, grouped by reason, one line per group with counts (name the individual files only when the group is small or the call is debatable).

**If nothing is over the cap:** say so, name the largest file and its line count as the headroom signal, and stop. Do not write a roadmap entry, and do not create `roadmap.md` just to leave it empty.

## Outcome — Roadmap Entries

Report first, ask second, in two turns — a structured choice hides any text sharing its turn (`_LOUIE_/guidelines/interaction-guidelines.md` § Content first, choice second).

### Granularity

- **K ≤ 5** → one roadmap entry per file. Default; no need to ask.
- **K > 5** → ask the user: one entry per file, or one grouped entry per top-level module/directory ("Refactor oversized files in `src/api` — 7 files, 9.4k lines"). Twenty single-file entries can drown a roadmap that is meant to hold epics.

### Entry shape

Add via `louie-roadmap add` semantics (`_LOUIE_/commands/louie-roadmap.md` § add) — the roadmap file, ID allocation, and `Last Updated` handling are that command's job, not this recipe's.

- **Title:** `Refactor <path> — <N> lines (over the 800-line cap)`
- **Source:** `audit`
- **Effort** (a suggestion the user may override): `S` under ~1000 lines, `M` for ~1000–1600, `L` above that.
- **Notes:**
  - `Measured YYYY-MM-DD at <short-sha>: <N> lines (cap 800, over by <over>).`
  - One line on what the file appears to do — the seed for deciding *how* to split it.
  - A suggested split axis where one is evident from the file's structure (by responsibility, by exported surface, by layer). Say nothing rather than guess.
  - `Re-measure before promoting — this count is a snapshot.`

### Re-run safety (required)

Before adding any entry, scan **both** `## Captured` and `## Promoted` for an existing entry referencing the same path.

- **Exists, file still over the cap** → do not add a second entry. Append the new measurement: `louie-roadmap-change <id> note "now <N> lines at <short-sha>"`.
- **Exists, file now under the cap** → report it as resolved and *offer* `louie-roadmap-change <id> status Done` (or `Dropped` if the file shrank for unrelated reasons and no refactoring happened). Never close an entry automatically — the audit measures, the user decides.
- **No entry** → add one.

Never delete a roadmap entry. Superseded entries get a status, not a removal.

## Follow-Up

Nothing in this recipe changes code. When the user wants to act on an entry:

- `louie-roadmap promote <id>` → `louie-feature --from-roadmap <id>` for a real split, with requirements, architecture check, review, and tests.
- `louie-update` when the split is genuinely under ~50 lines of movement (rare for an 800-line file — usually it isn't).

If the user asks to "just fix them" while this recipe is loaded, route to those commands rather than editing files here. An audit that quietly starts refactoring bypasses the feature-doc gate.

## Variations

- **Different threshold** — pass one for the run (`quality:file-length 500`). Report the threshold used in the header; the guideline stays untouched.
- **Warn band** — additionally list files within 100 lines of the cap as *approaching*, reported but never filed to the roadmap. Useful as a trend signal on a codebase already at zero violations.
- **Scoped audit** — one subpath, one package of a monorepo, or one language.
- **Logical lines** — count non-blank, non-comment lines instead of physical lines. Changes what "800" means relative to the guideline; state the unit prominently in the report and in every entry's Notes if you do this.
- **CI mode** — emit the over-cap list as machine-readable output (path + count) and skip the roadmap step entirely, for a pipeline that just wants a pass/fail signal.
