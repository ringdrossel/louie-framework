# Framework Changelog

Internal version log for the LOUIE framework. Tracks meaningful changes to the framework itself — not user project artifacts. Entries here inform what `louie-update-framework` users see when they pull a new version.

Format: reverse chronological, date + short description + affected areas.

## Unreleased

- **Leo (Designer) now proposes and discusses before writing — no more silent design.** Previously Leo read the context and produced a full component tree / props / styling / accessibility spec straight into the feature doc with no user feedback. He now follows the same Proposal & Discussion Gate as Sophie: present a lightweight proposal (layout & user flow, key UX decisions, tradeoffs, accessibility approach), discuss conversationally, loop until the user explicitly approves, and only then finalize the design into the feature's `feature.md`. "They didn't object" is not approval; even a delegated decision needs an explicit go-ahead. Updated: `_LOUIE_/agents/designer.md` (new `## Process` section with the gate; Output Format clarified to write after approval into `feature.md`), `_LOUIE_/commands/louie-feature.md` (step 9 notes the gate), `_LOUIE_/workflow/ai-workflow.md` (Scenario 1 Step 4 notes the gate). No change to when Leo runs (still UI-only, skipped for backend features) or to the handoff to Nina.
- **Branch mode (`current` / `ask`) and new `louie-branch-mode` command — branch-per-feature is no longer the default.** Per-project setting controlling whether `louie-feature` branches. `current` (new default) works on the current branch, including `main` — LOUIE never creates a branch on its own and never prompts; a branch is created only when the user explicitly asks. `ask` prompts at the start of each new feature (create `feature/<name>` or stay put). Scope is `louie-feature` only — `louie-extend` / `louie-update` / `louie-bugfix` always run on the current branch. Persisted in `_LOUIE-output/runbook.md` under a new `## Branch Mode` section (tool-agnostic). Set non-interactively to `current` during `louie-setup` (no question — the whole point is to stop asking) and changeable anytime via `louie-branch-mode`. Retired the framework-dev Critical Rule *"Never commit directly to local `main`. All work happens on a feature branch"* (root `CLAUDE.md` only — it never shipped in the init-script Critical Rules); the distributed *"Never merge to `main` without approval"* gate is kept but is inert in `current` mode. New files: `_LOUIE_/commands/louie-branch-mode.md`, `_LOUIE-internals/branch-mode.md`. Updated: `_LOUIE_/commands/louie-feature.md` (new step 8 — branch handling reads the mode; later steps renumbered), `_LOUIE_/commands/louie-setup.md` (step 5c — sets `current`, no question), `_LOUIE_/templates/runbook-template.md` (new `## Branch Mode` section), `_LOUIE_/guidelines/coding-guidelines.md` (Git Discipline reworded — branching is Branch-Mode-governed, merge gate conditional), `CLAUDE.md` (rule 4 replaced, command added to table), `README.md`, `_LOUIE_/workflow/ai-workflow.md`, `_LOUIE_/setup/project-setup.md`, all six init scripts (claude/cursor/codex/gemini/opencode/pi × sh/bat), and the internals index.
- **New command `louie-evaluate`** — whole-codebase standards assessment that produces persistent, triaged findings and drives an optional step-by-step correction loop. Distinct from `louie-review` (which is per-feature, chat-only, LOUIE-only, gate-before-merge): `louie-evaluate` is whole-codebase or subpath, writes persistent files to `_LOUIE-output/evaluation/`, works on foreign/non-LOUIE code, and has a built-in apply loop. Two modes dispatched on `_LOUIE-output/architecture.md` presence — **LOUIE mode** (uses the project's own architecture/runbook/tech-stack + coding-guidelines as the lens; skips Sophie's structural pass) and **non-LOUIE mode** (Sophie does a light structural pass into `codebase-map.md`; Max evaluates against `coding-guidelines.md` only, then recommends `louie-import`). Max emits three-tier findings (Critical / Should Fix / Suggestions) across code quality, dead code, DRY, over-engineering, security baseline (+ architecture-compliance and runbook-drift in LOUIE mode), each with a stable ID. Output schema: `summary.md` + `findings.md` always, plus dedicated files for the four high-volume categories (`code-quality.md`, `dead-code.md`, `dry-violations.md`, `over-engineering.md`); low-volume categories (security, architecture, runbook) stay in `findings.md` to avoid stub files; small projects (<~15 findings) collapse to a single `evaluation.md`. Phase 2 apply modes chosen upfront: **walkthrough** (default, per-finding apply/modify/skip/defer/quit), **apply-all** (every finding, ALL THREE TIERS incl. Suggestions, unattended — only safety net is a failure pause; no cross-cutting confirmation brake), or **no** (exit, files saved). Re-runs offer continue / rescan / archive / quit; pending+deferred findings survive across sessions. Apply phase routes through existing gated flows (`louie-bugfix` for real bugs, `louie-update` for small cleanups) so the Three Critical Rules stay intact; non-LOUIE mode warns once that changes won't produce LOUIE artifacts. **No new agent** — reuses Sophie (structural pass), Max (standards lens), Nina (apply-time only). New files: `_LOUIE_/commands/louie-evaluate.md`, `_LOUIE-internals/evaluate.md` (design rationale). Registered in `CLAUDE.md`, `README.md`, `_LOUIE_/workflow/ai-workflow.md` (new Scenario 7, Product Ideation → 8, Capture-an-Idea → 9), all six init scripts (claude/cursor/codex/gemini/opencode/pi × sh/bat), and the internals index. Smart-merge on rescan (carry status forward by file:line + signature match) deferred to `BACKLOG.md`.
- **Runbook `Common Gotchas` section removed — operational reference only.** The accumulating gotchas list had become a write-only sink: every entry took a slot, only a few were relevant to any task, and the irrelevant ones diluted LLM context. Operational caveats now live **inline** as parentheticals next to the entry they affect (Notes column on Ports & Endpoints, sub-notes on Environment & Dependencies). Implementation learnings (framework quirks, cache rules, "running locally needs Z env var or it silently defaults") move to two places that already exist and serve the LLM better: a one-line `// WHY` comment next to the code that bites, and the per-feature `bugfixes/<slug>.md` (new mandatory **Detect / Avoid** section in the bugfix template — the canonical home for that knowledge). Bugfix Runbook-Update step is no longer mandatory; most fixes don't change operational surface and that's expected. Debugging table caps at ~10 rows; prune older symptoms caught by tests/monitoring. Updated: `_LOUIE_/templates/runbook-template.md` (section removed, Notes-column guidance added, Maintainers note rewritten), `_LOUIE_/templates/bugfix-template.md` (new Detect/Avoid section, Runbook-Update now conditional), `_LOUIE_/templates/bugfix-prompt-template.md` (step 9 rewritten), `_LOUIE_/templates/bugfixes-overview-template.md` (cross-ref updated), `_LOUIE_/agents/architect.md` (skeleton instructions + subsequent-run guidance), `_LOUIE_/agents/coder.md` (Step 1 reading, Step 5 update rules rewritten, Step 5b bugfix flow), `_LOUIE_/agents/reviewer.md` (§ 7 Runbook Coverage rewritten — now flags implementation-learning entries as Should Fix), `_LOUIE_/commands/louie-bugfix.md` (no mandatory runbook entry; detect/avoid lives in the bugfix doc), `_LOUIE_/commands/louie-review.md`, `_LOUIE_/commands/louie-review-doc.md`, `_LOUIE_/commands/louie-review-mode.md` (anchor reference updated), `_LOUIE_/commands/louie-update.md`, `_LOUIE_/recipes/docker/build-push.md` (Common Gotchas seed replaced with inline Notes + a Debugging row), all six init scripts (descriptor updated). Migration prompt for downstream projects: `ressources/cleanup-runbook-gotchas.md`.
- **Review mode (`manual` / `auto-fix-critical` / `auto-fix-all`) and new `louie-review-mode` command** — per-project setting that controls whether `louie-review` stops for human approval after the verdict (`manual`, current behavior) or auto-hands `Critical` + `Should Fix` (and optionally `Suggestions`) to Nina in a review→fix→review loop. Three modes: `manual` (safe default; current behavior), `auto-fix-critical` (auto-applies Critical + Should Fix in a loop, surfaces Suggestions at the end for approval), `auto-fix-all` (also auto-applies Suggestions). Loop is capped (default 3 rounds, configurable in runbook) with a regression guard that stops immediately if a fix round introduces a new Critical; on cap-hit, fall back to `manual` for the remainder. Mode is persisted in `_LOUIE-output/runbook.md` under a new `## Review Mode` section (tool-agnostic — works across Claude Code, Codex, Gemini CLI, opencode, pi, Cursor) and is set during `louie-setup` (Tom asks; no silent default) or `louie-import` (Tom asks; recommends `manual` for imports since unknown invariants raise risk). Per-call override on `louie-review` (e.g. `louie-review auto`, `louie-review manual`, `louie-review auto-fix-all`) does **not** mutate the runbook. New command `louie-review-mode` shows the current setting and lets the user change it project-wide. Nina's "address review findings" handoff is narrow by design: apply listed items in order, run typecheck/tests/build per `tech-stack.md`, never self-repair test failures (boundary clean — failures become a new Critical in the next round, regression guard handles it). The single Change History entry is written by Max at loop end with the round count and outcome (e.g. `Max review (auto-fix-critical) — 2 rounds, 1 critical + 4 should-fix resolved, 2 suggestions deferred`). New files: `_LOUIE_/commands/louie-review-mode.md`, `_LOUIE-internals/review-mode.md` (design rationale). Updated: `_LOUIE_/commands/louie-review.md` (mode dispatch + override syntax), `_LOUIE_/commands/louie-setup.md` (step 5b — Tom asks), `_LOUIE_/commands/louie-import.md` (step 10b — Tom asks, recommends manual), `_LOUIE_/agents/reviewer.md` (new "Auto-Fix Loop" section with cap + regression guard + test-failure protocol), `_LOUIE_/agents/coder.md` (new step 5c — narrow "address findings" mode), `_LOUIE_/agents/analyst.md` (pointer to setup/import questions), `_LOUIE_/templates/runbook-template.md` (new `## Review Mode` section placeholder), `CLAUDE.md`, `README.md`, `_LOUIE_/setup/project-setup.md`, all six init scripts (claude/cursor/codex/gemini/opencode/pi × sh/bat) to register the new command. Slim Mode and `louie-bugfix` are unaffected. `louie-review-doc` is unchanged for now — same surface in `manual` mode; nearly identical to `louie-review` in auto modes (differs only in whether docs are updated). Open design questions resolved during implementation: (1) Suggestions still surface for approval at end of `auto-fix-critical` (not skipped); (2) Nina always bounces back to Max on test failure, no self-repair pass; (3) `louie-review-doc` kept, may be revisited later.
- **Six init scripts now ship per AI tool — Claude Code / Codex / Cursor / Gemini CLI / opencode / Pi Coding Agent** — extending the per-tool init pattern (`_LOUIE_/setup/<tool>-init.sh/.bat`) beyond the original three. Gemini CLI writes `GEMINI.md` (hierarchical context-file convention); opencode and pi.dev both write `AGENTS.md` (their native conventions, identical to Codex's — kept as separate scripts for discoverability, all idempotent via the shared `<!-- LOUIE-FRAMEWORK -->` marker so running multiple is safe). No changes to existing scripts. Updated: `README.md`, `_LOUIE_/setup/project-setup.md`, `_LOUIE_/commands/louie-update-framework.md`, `_LOUIE-internals/core.md` to reference the new scripts.
- **Second recipe: `docker:build-push`** — simple containerisation flow producing three artifacts (Dockerfile + dev-side `buildpush.sh` + server-side `update.sh`) for projects shipping a single image to a single registry, deployed to a long-lived server by `docker run`. Scope locked at v1: one image, one Dockerfile, one registry per invocation; orchestrators (K8s/ECS/Cloud Run/Nomad), multi-arch, CI integration, compose-based dev, image scanning/SBOM/signing, and blue-green deploys are all explicitly Variations or out of scope. Registry identity (host, image-path prefix, tag strategy, base-image policy) lives in `_LOUIE-output/tech-stack.md` under a new **Container Registry** subsection that Sophie adds during her eval — registry choice is build/deploy-time configuration, not a runtime component, so it does **not** belong in `architecture.md`. Operational details (`docker login` command for the chosen registry, build/push/deploy commands, `--env-file` contract, port mapping, restart policy, accumulating gotchas) go in `_LOUIE-output/runbook.md`. No new top-level artifact, no new recipe-parameter mechanism in the dispatcher — user-interaction happens inside Tom's interview, seeded by the recipe's Requirements Seed. Locked design choices the recipe fixes from the source material: (1) tag from current `HEAD` via `git describe --tags --exact-match` / `git describe --tags` / `sha-<short>` rather than "highest version tag in the repo" — and actually apply the resolved tag to the image rather than computing it and pushing only `:latest`; (2) `--env-file /path/to/.env.production` for all runtime configuration instead of inline `-e SECRET=…` on the `docker run` command (anti-pattern leaks via `ps aux`, shell history, container metadata); (3) pull before stopping in `update.sh` so a registry failure does not leave the host with no running container and no image to start; (4) non-root `USER` baked into the image, not relied on `docker run --user` at deploy time. Default single-arch (matches typical single-VM deploys); multi-arch via `buildx` is a Variation. Recipe ships three Dockerfile patterns — single-package app, monorepo with shared lib + multiple consumers, generic non-Node compiled binary — and lets Nina pick after reading the project; Sophie validates the pick. `.dockerignore` and pinned base-image versions are required cross-pattern. Recipe does **not** call `docker login` or write credentials anywhere; it documents the per-registry login command in `runbook.md` and lets operators run it once per machine. New files: `_LOUIE_/recipes/docker/README.md`, `_LOUIE_/recipes/docker/build-push.md`. No changes to the dispatcher, agents, templates, init scripts, `CLAUDE.md`, `README.md`, or any downstream-distributed file beyond the recipe addition itself — recipe sections auto-discover, the existing chain executes unchanged, and the registry-choice slot in `tech-stack.md` is added by Sophie per-project rather than baked into the template (avoids forcing a registry section onto every project regardless of whether the recipe applies). Source material grounded in a real-world Node monorepo (React client + Express server + shared TS lib + Drizzle migrations); reference files captured under `_LOUIE-internals/examples/docker-build-push/` (not distributed). BACKLOG unchanged — `docker:build-push` was not on the candidate list; closest related entry remains `dev:docker-compose`.
- **Per-project roadmap added** — new artifact `_LOUIE-output/roadmap.md` for capturing pre-feature-folder ideas, with a `louie-roadmap` command for adding and promoting entries. Fills the gap between `louie-ideate` (chat-only, ideas evaporate) and `louie-feature` (full chain, full commitment) — captured ideas persist with the lightest possible schema (ID + Title + Created + Source + Notes; optional Effort; never Priority/Owner/Dependencies, which belong on a feature doc). v1 subcommands: `add` and `promote`; bare call prints the current roadmap. No agent owns it (same as `runbook.md`) — the command writes directly. `louie-ideate` now ends with a three-bucket sort (pursue now / save to roadmap / drop) instead of dumping ideas into chat. `louie-feature` accepts `--from-roadmap <id>` to seed Tom with a captured entry; on success, the entry moves from `## Captured` to `## Promoted` with a back-link to the feature folder (auditable trail). `roadmap.md` is lazy-created on first `add` — no init-script bootstrap, no migration step, existing LOUIE projects gain the feature automatically. New files: `_LOUIE_/commands/louie-roadmap.md`, `_LOUIE_/templates/roadmap-template.md`, `_LOUIE-internals/roadmap.md` (design rationale).
